## KOS 作为全系统底层的后续方向（2026-11-23）

主人再次明确：KOS 应成为整个 Umeda 的底层。下一阶段围绕一个项目，连接目标、行动、
知识、Agent 执行、工作记录和成果；KOS 自身的逻辑优化与融合一起设计、一起推进。
本次仅记录方向，不启动实现或迁移，也不将旧 KOS 的目录、对象状态或 Agent 流程原样定为新合同。

- Umeda 是应用总入口，提供交互、设备、权限和执行能力；KOS 承载各入口、设备与 Agent
  共用的长期工作与知识信息体系，包含对象、关系、来源、版本和成果。工作台、阅读器、
  工作管理和伙伴页面是消费该体系的不同视图，插件／WebView 是当前交付方式。
- 下文 2026-11-22 将 KOS 限定为「知识库资源」的范围以本节为准；应用级业务服务继续
  承担唯一写入职责，不恢复两套项目状态，也不要求所有信息存入同一个数据库。
- 具体方案先核对 kos-framework 的目录演变、对象及生命周期、知识与行动工作流、
  Skill、上下文和校验反馈，再共同优化；不能只从当前工作台的界面和简化业务字段反推旧设计。
- 首批目标是项目闭环：关联资料与工作事项，按请求交给 Agent 执行，保存有来源的成果与
  工作记录，再由另一个引擎读取同一份相关信息继续工作。实现顺序和验收见
  [路线图](../umeda-optimization-roadmap.md#kos-底层融合与逻辑优化2026-11-23待实施)。
- 共用信息不意味着默认加载整库背景。沿用主人提示后按需读取、业务事项与执行 Session
  分离、人工判断不由 Agent 冒认的边界；不另建 KOS 专属执行循环。

状态：方向已记录，详细逻辑与实施方案待后续共同设计；不表示统一对象关联、检索、
旧库迁移或跨端闭环已经交付。

## 产品组合关系（2026-11-22，范围按上节更新）

Umeda 是应用，是一切交互的入口和能力组合的宿主。空间、伙伴、项目／任务、Agent 接入、
知识库、设备与工具都组合在 Umeda 内，不与 Umeda 并列成几套产品或上层系统。

- 空间、目标、项目、行动与工作记录用于组织 Umeda 中的工作。
- 伙伴是 Umeda 中长期协作的 Agent 身份与配置；实际执行可切换所接入的引擎。
- 接入的 Agent 承担理解、规划、执行，以及知识的读取、理解、整理、生成与写入。
- KOS 的知识内容包括材料、笔记、摘录、研究产物、知识／方法和来源关系；其整体范围
  按上节扩展为长期工作与知识信息体系。KOS 不指一个独立的知识管理 Agent 系统，
  不拥有专属大脑、Agent loop、调度器或必需的 DSH 后端。
- Umeda 的客户端基础设施提供知识内容的存取、索引、展示、同步与可恢复性，并将工具
  能力交给接入的 Agent；这些基础设施不等于 KOS 自己具备理解和执行能力。

原设计中的「KOS Agent 基于 DSH」是历史方案。新的关系是「Umeda 接入 Agent，Agent 使用
KOS 知识库」；如果未来接入 DSH，也是 Umeda 的一种 Agent 接入方式，不恢复 KOS 专属后端。
以下文档中的工作组织、执行与知识资源均为 Umeda 内部职责，不构成与 Umeda 并列的三层产品。

## 范围与取舍

Umeda 是主人自用的工作、阅读、知识与生活终端。手机负责随手记录、阅读、查看进展和下发
意图，电脑提供完整的 Agent 与本机执行能力，各入口围绕同一份工作持续推进。长期目标是
一个能理解工作背景、保留成果并持续协助的个人助手，不能只累加看板或聊天入口。

本方向只作用于 Umeda 个人分支，不改变普通 Cindy 的账号、插件、共享与发布契约。
个人模式已选择免账号、免扫码配对，不把恢复这些流程列为本路线图的前置条件。
凭证不入仓、插件隔离、数据归属、兼容与可恢复性仍遵循仓库专项规则。

技术取舍以体验、正确性、可靠性、可维护性和能力完整性为先。不以节省开发工作量或赶进度
作为保留明显体验缺口的理由。实现复杂度也不是质量证明：替换框架须给出可以验证的改善，
不能把“原生”“Swift”或“共享代码更多”直接等同于最佳方案。

## 像应用一样使用资料

正常路径是：打开应用即可记录和阅读，资料库由应用自动创建并维护。使用者不需要先建立
目录、安装 Obsidian、选择 Vault 或编辑 JSON 配置。工作台、资料库与任务是统一产品里的
不同入口，不要求理解插件的打包与安装。

- 默认资料库由应用管理；导入、导出、备份、恢复是明确的产品能力。
- Markdown 与普通附件保持可迁出、可用其他工具读取；开放格式不等于要求用户管理磁盘布局。
- 外部目录连接可以作为高级能力保留，明确其与应用托管库的归属，不同时维护两个主写库。
- 已有资料的迁入保留原件，先复制、校验再切换；不能以“整理”为由直接搬走或改写原库。
- 离线能打开已保存的内容并继续编辑；未下载的附件明确可见其状态，不能显示成内容丢失。
- 保存、同步、备份是不同承诺。界面能够区分“本机已保存”“等待同步”“已同步”“存在冲突”，
  不把拿到云端回执称为已完成备份。

现有桌面插件是可用的交付形态。目标中的统一入口不要求先改插件基座或拆掉旧插件；
Umeda 的通用资料库服务进入客户端基础设施。按 2026-11-22 的新分工，旧 KOS 的目标、项目、
行动管理上移到 Umeda 应用级服务，与知识内容共同构成 KOS 底层，由接入的 Agent 按需使用。这一区分只作用于个人 Umeda，
不将 KOS 垂直业务或新的工作管理规则硬编码进普通 Cindy Core。

## React 与原生共同服务体验

保留 React 对社区富交互组件的承载能力：编辑器、看板、阅读标注、关系图、图表与流程画布
可使用 Web React。React DOM 组件与 React Native 组件不是直接通用的；Web 组件进入 iOS
需要合适的 WebView 内容面，仍要验证触摸、输入法、选区、键盘和无障碍。

客户端承担资料与执行的事实；界面消费这些事实。平台导航、文件导入、系统分享、小组件、
生命周期与通知交给宿主及适合的平台 API。需要原生实现的局部可用 Swift／UIKit／AppKit
等接入，不预设整应用重写。桌面 Electron、手机 React Native 是否替换，单独以可复现的
体验收益和既有能力不退化作裁决。

混合架构是目标架构本身，不是等待全量 Swift 重写的过渡承诺。

## 多端连续性与真实边界

阅读和资料管理的可用性不依赖 Mac 在线；云端副本可供其他端下载，本地保存供离线使用。
重连自动补齐变化，但后台运行遵循系统调度，不能承诺 iPhone 永久保持连接。

指令链路必须区分手机已保存、云端已接收、执行电脑已接收、Agent 正在执行和结果完成。
Cloudflare 当前承担中转、资料副本和指令收件箱，Agent 仍在执行电脑上运行。
Mac 处于真正休眠时不能执行指令，进程未退出不代表正在运行。需要全天候执行时，另行选择
常在线的执行设备，并复用执行与恢复协议，不靠隐藏状态文案掩盖离线。

## Agent 与知识的后续关系

先完成资料、阅读、记录、搜索、同步与恢复的基础，再优化研究、提炼、规划和综述的完整
Agent 链路。不直接恢复旧 Obsidian + DSH 的全部行为，不将更换 harness 当作质量改善。

未来多个 Agent 通过明确的知识服务共享文档、版本、引用和经整理的项目背景；保留各自的
运行记录与上下文窗口，不能默认相互复制整个聊天历史。产出应能追溯来源与使用版本，
建议、写入和执行结果分别记录，并能复核、修改和撤回可撤回的动作。
这些是后续要求，当前工作台未实现通用的跨 Agent 上下文服务。

输出质量以实际样本评价：引用是否准确、结论是否有依据、结构是否有用、是否保留未知项、
写入是否正确、重复运行是否制造重复成果，以及人需要做多少修订。评测结果再决定模型、
检索、上下文组织与 harness 的调整，避免只优化提示词篇幅。

## 统一 Agent 入口与工作／个人空间（2026-11-22）

主人希望 Umeda 成为工作、个人开发、学习和生活中与 Agent 交互的总入口。工作设备使用组织
提供的模型连接，个人设备使用个人模型连接；统一入口需要同时承载这些使用场景。以下为
产品目标与方案，不表示已完成数据模型、跨空间同步或外部 Agent 的实时接管。

- 默认按工作与个人两个空间组织项目、资料、执行位置和模型来源。空间是产品数据与路由
  的边界，不把不同来源的 key 汇总进一个可任意回退的供应商池；原有个人免账号／免扫码
  决策保持不变。连接凭证由执行设备保存，控制端不需要获得执行设备的 API key。
- 项目和工作事项属于 Umeda，不绑定某个模型、Harness 或原生聊天编号。当前 Cindy 的
  Session 在用户界面仍称「任务」；本方案用「工作事项」区分持续的工作目标与底层执行任务，
  正式 UI 命名前继续遵守术语表。伙伴是可选的长期协作入口，不强迫每项工作先创建伙伴。
- 同一工作事项能够从 Codex 交给 Claude Code 等已接入引擎，保留目标、决定、工作现场、
  证据和待办。原生上下文能续接时复用，跨引擎通过有界交接与原始历史检索继续，不能承诺
  转移全部原生上下文、运行进程、工具句柄或模型隐含状态。
- 保留原生 Codex、Claude Code 等工具的使用方式。外部记录接入与 Umeda 内运行共用项目
  归属；历史导入不等于持续双向同步，也不等于能接管仍在运行的外部进程。
- 主人明确选择跨端查看「做了哪些工作」并下发指令，不需要多端查看代码。代码、diff、
  原始工具输出、完整引擎上下文与连接凭证默认留在执行设备；其他端消费工作记录和状态
  投影，不把工作代码仓库同步到个人资料库。具体中转与存储部署另在实施时核对。
- 工作记录应说明目标、实际完成的工作、结果、验证、未完成事项和需要主人决定的事，
  关联项目、执行设备、引擎与时间。记录不要求主人检查代码或逐工具调用，也不将 Agent
  自述当作验证结果。允许从记录直接继续工作、补充要求、停止或切换底层引擎。
- 其他端发起办公工作时，指令送到办公电脑，由该机上的 Agent 使用公司模型连接执行；
  个人设备是控制入口，不获得公司 API key。电脑休眠／离线时保留未送达意图与真实状态，
  恢复可执行条件后继续；远程启动 Agent 不等于已经实现远程开机或物理唤醒。
- 所有记录带空间、项目、来源、执行设备与执行路由；在各自允许的范围内统一检索。工作
  经验与学习内容可经显式整理进入个人知识库，默认不把工作原始上下文加入个人记忆。

数据层次、引擎交接与最小验收见[客户端架构](../dev-rules/umeda-client-architecture.md#统一-agent-入口与可交接工作事项方案2026-11-22)。

## 旧 KOS 工作对象归入 Umeda（2026-11-22，KOS 范围按 11-23 更新）

主人确定把旧 KOS 的 Goal／Project／Task 业务上移到横跨设备与 Agent 的 Umeda 应用层。
其中知识部分存放原始材料、摘录、摘要、研究产物、知识／方法和证据；
读取、理解、研究、整理与写入由 Umeda 接入的 Agent 完成。展示与内容服务由 Umeda 提供。
当前 0.4.0 仍从 Markdown 解析旧业务对象，本节不表示已经完成迁移。

| 组合进 Umeda 的部分 | 职责 |
| --- | --- |
| 工作组织 | 长期目标、项目、行动事项、计划／排期、业务进展、工作记录与结果验收 |
| 伙伴与 Agent 接入 | 长期协作身份及实际理解、规划、执行和知识读写能力 |
| KOS 知识库资源 | 材料、书籍、批注、摘录、研究产物、知识／方法、内容关系与证据 |
| Umeda 客户端基础设施 | Agent 运行、设备连接、工具、资料存取、展示、索引、同步与恢复 |

- 业务目标说明要取得什么结果，项目组织持续工作，行动事项说明具体要做什么。它们不依赖
  某篇 Markdown、某位伙伴、某台设备或某个引擎存在，也不要求属于代码仓库。
- 业务行动事项（旧 KOS 的 `type: task`）与 Cindy 执行任务（Session）不是一一对应：事项
  可以先计划、由人完成而没有 Agent 运行，也可关联研究／实施／复核等多段执行。业务层
  复用 Session 的执行事实，不能再实现输入队列、引擎切换或重试循环。
- 业务目标不是 Cindy 的 Agent 目标模式，项目不是代码目录，事项完成也不等于模型一轮
  回复结束。业务状态依据约定的结果与验证推进，需要人的结果判断仍由人作出。
- KOS 文档通过稳定引用关联应用级目标、项目、事项和成果；工作管理引用知识与证据。
  规划与知识可以互相使用，但不各维护一套项目／事项状态。
- 今日工作台、目标进展、项目看板、排期与工作复盘中的事实部分属于应用级工作管理。
  日记、认知反思与经整理的方法可以留在知识侧，引用工作记录而不复制另一份执行状态。
  可执行 Skill 由现有能力运行时装配，知识中的方法说明可成为其来源，不强制等同。
- 旧目标／项目／事项文档及其正文、未知属性、关系、状态与证据保留。迁移先建立稳定身份
  与来源映射，再切换唯一写入归属；不通过批量删除、重命名或将旧 Task 强转为 Session 完成。
  Markdown 可以继续作为说明、兼容来源或导出格式，业务归属上移不要求主人搬文件夹。

具体边界与迁移见[客户端架构](../dev-rules/umeda-client-architecture.md#目标项目行动与知识的分层2026-11-22)。
