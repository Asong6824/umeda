# Umeda 用户故事：统一工作、知识与 Agent 入口

> 日期：2026-11-22。本文保存产品预期与验收场景，不表示这些能力已经实现、部署或安装。
> 产品边界见[产品方向](umeda-product-direction.md)，实现职责见
> [客户端架构](../dev-rules/umeda-client-architecture.md)，进度见
> [优化路线图](../umeda-optimization-roadmap.md)。仅作用于个人 Umeda 分支。

## 阅读约定

Umeda 是应用与能力组合的总入口。伙伴、Agent 接入、工作组织、KOS 知识库及设备能力均在
Umeda 内。KOS 保存知识，由接入的 Agent 理解与读写，不再拥有独立的智能后端。

本文的「业务任务／行动事项」承接旧 KOS 的 Task；「执行任务（Session）」指现有 Cindy
中承载消息与 Agent 运行的条目。两者可关联，但不要求一一对应，也不在本文裁决正式 UI
命名。沿用[任务与对话命名规则](task-and-conversation-naming.md)。

八个故事共同约束目标体验。其中第八个故事的「主人手动提示、按需加载」是明确的产品
约束；伙伴默认入口、外部记录持续收录方式和主动协助程度仍需后续细化，不能从示例推出
默认监控全部活动、自动执行全部计划或读取全部业务背景。

## 1. 在手机上继续办公电脑里的工作

主人在手机中明确要求继续某个办公项目，例如分析一个失败问题并整理方案。Umeda 能定位
该项目与已有进展，将意图交给指定办公电脑上的 Agent，使用该设备上的公司模型连接执行。
主人在手机上查看进展、结论和待决定事项，不必下载代码、操作终端或把公司 API key
复制到手机；执行产生的记录归入同一项目。

验收关注：设备、模型来源与项目归属明确；显示待送达、执行中与完成的真实状态。办公
电脑真正休眠或离线时保存意图并说明状态，不把云端接收当成已经开始执行，也不承诺物理唤醒。

## 2. 同一件工作随时更换 Agent

主人用 Codex 开发个人项目，随后要求 Claude Code 继续完善阅读体验。新的执行者接着
当前工作的目标、约束、决策、修改现场、待办和验证证据继续，不要求主人手工抄写交接说明。
以后再换回 Codex，工作身份、关联和进展保持连续。

验收关注：保留真实工程现场，结果未知的副作用不重复执行；区分 Agent 自述与验证事实。
这是当前执行的连续性，不是把全部目标／项目／业务任务加载给新引擎。需要新读或刷新
业务管理数据时遵循故事 8；不承诺复制原生推理状态或所有工具进程。

## 3. 在外部工具开发，也能形成有依据的工作记录

主人白天直接使用原生 Codex 或 Claude Code，晚上在 Umeda 中询问某个项目今天完成了
什么、还有什么未完成。Umeda 根据已接入的记录整理目的、进展、结果、验证和遗留问题，
关联来源；没有收录或无法核实的部分明确说明，不靠猜测补齐。

验收关注：保留原生工具使用习惯；重复收录不产生重复记录；历史导入、持续收录与实时
接管的状态分别可辨。看到外部执行不代表取得控制权，不同时驱动同一个原生 Session。
持续接入范围另行明确，不默认扫描全部历史或收集与项目无关的活动。

## 4. 阅读、思考与知识积累连起来

主人在 iPad 阅读、划线和写笔记，并要求比较当前观点与以前读过的材料。所选 Agent
按请求读取相关内容，形成有来源的比较；主人可将值得保留的结论写入 KOS。以后在电脑
写文章或推进项目时，可以继续检索并使用这些知识。

验收关注：打开应用即可阅读和记录，无需先建立目录、管理 Vault 或安装 Obsidian。
已保存内容离线可用，未下载内容状态明确；结论保留来源与版本。知识整理属于 Agent
能力，KOS 负责保存资料和成果，不自行触发另一套智能流程。

## 5. 目标、项目、任务与知识相互关联

主人提出一个三个月的学习目标，并计划通过小项目实践。Umeda 维护目标、项目和具体
业务任务的关系、状态及进度；读书笔记和研究材料保存到 KOS，按需关联这些工作对象。
主人能回看推进了什么、留下了什么知识、距离目标还有哪些差距。

验收关注：任务可以由人完成而没有 Agent 执行，也可关联研究、实施、复核等多段执行；
不强迫所有交流先创建完整层级。一次模型回复结束不自动代表业务任务完成；KOS 文档
与 Umeda 工作管理不各维护一套项目状态。Agent 访问这些业务对象仍由主人按故事 8 触发。

## 6. 伙伴提供连续协作身份，执行引擎可以更换

主人与一位伙伴长期讨论学习、开发和生活安排。伙伴保留主人明确提供且允许使用的
偏好与协作背景；底层引擎从 Claude Code 换为 Codex 时，持续协作身份与已有工作关系
保留。主人也可以直接进入项目或发起临时工作，不必先选择或创建伙伴。

验收关注：伙伴身份、执行引擎和应用业务数据各有归属。伙伴连续性不意味着默认读取
所有目标、项目、任务或整份知识库；业务背景加载遵循故事 8。是否以伙伴作为默认入口
仍待细化，不以该故事强制改变首页或所有工作入口。

## 7. 打开应用即可了解自己的进展，并按意图推进

主人早上查看工作进展、个人项目、阅读计划与待决定事项，然后明确提出可用时间和安排
请求。Agent 按该请求读取所需范围，结合真实进度提出建议；主人确定后，可进入阅读、
继续项目或向指定设备下发执行意图。晚上回顾时能看到有依据的进展与成果。

验收关注：首页／看板直接展示业务数据，不因此将数据注入 Agent。建议、排期和实际
执行分别记录，不凭一次建议自动启动全部计划；定时主动协助的范围与触发另行确定。
未请求读取时保持故事 8 的上下文边界。

## 8. 共用目标、项目、任务，由主人提示后按需加载

主人在 Umeda 中维护之前 KOS Vault 里的目标、项目、任务及其关系、状态和进度。
各 Agent 通过同一应用服务访问这些记录。主人可以在界面维护，也可以明确指示某个
Agent 帮忙读取和更新；无需在不同引擎的聊天里各维护一份。

普通交流默认不装载这套管理系统的数据。主人明确提出「读取某个项目的任务再继续」
时，Agent 才读取与请求相关的对象；需要更多背景时针对性读取。主人要求把本次成果
更新到业务任务后，更新进入同一份记录，供后续明确读取时使用。

以下为该行为的产品正本约束，架构与路线图引用本节：

- **共享业务事实**：目标、项目、任务具有稳定身份与统一状态，独立于 Agent 的聊天历史。
  共用遵循所属空间与数据范围，不因接入多个引擎而混合所有资料。
- **由主人提示触发**：明确要求读取、比较、规划或更新相关对象即可表达意图，无需特殊
  口令或额外确认。仅打开应用／项目、选择伙伴、切换引擎或发生同步，不触发背景自动加载。
- **按请求限定范围**：可只读单个任务、某个项目或目标概况；关联笔记、书籍与证据也按需
  获取，不默认递归读取所有关联内容。选择引擎不改变请求范围。
- **界面投影与模型上下文独立**：看板、目录和进度可以直接展示并同步；展示的数据不因此
  进入 system prompt、默认消息、隐藏摘要或伙伴记忆，不用这些途径绕过按需读取。
- **更新不向对话广播**：数据更新不自动写入其他 Agent 的已有上下文，也不后台重写各段
  对话。其他 Agent 后续明确读取时获得最新版本；冲突和旧版本如实处理。
- **已读内容有实际生命周期**：按请求读到的内容会成为该次交流与工具记录的一部分；
  不承诺读取后自动抹去模型已获得的信息。当前执行的已有上下文与有界交接可保持连续，
  切换本身不额外读取或刷新整套业务管理数据。
- **独立维护与执行**：持久业务记录不依赖某个 Agent 在线；本次读取、交流或执行结束
  不删除它们，也不据此自动标记业务完成。KOS 保存知识，Umeda 维护工作组织与关联。

最小验收：无相关请求时交流与切换引擎均不新增业务背景；明确只读一个任务时不装载整个
项目或看板；一个 Agent 更新记录后，另一个 Agent 的对话不被推送改写，随后主动读取
能取得新版本；单纯打开看板不产生模型调用或隐式背景装载。

## 与实现进度的关系

故事 1、4、5、7 可复用现有远程执行、资料库和旧工作台能力，但完整体验仍有缺口。
故事 2 的结构化检查点已完成首个源码切片，不表示完整工程交接已经验收；故事 3 的
已有历史导入不等于持续收录。故事 5、8 已有本机业务对象与按需读写工具的首个源码切片，
支持一句话更新任务／项目／目标进度；独立管理界面、旧对象迁移和跨端业务同步仍待实现，
不能因为旧 KOS 页面已经显示这些对象而标记完整完成。具体进度以路线图和交付台账为准。
