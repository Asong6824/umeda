# KOS 卡片与白板：实现范围与后续

## 产品决定（2026-11-24）

主人选择采用 Heptabase 的 Card / Whiteboard 模型，降低旧 KOS 对象、生命周期和数据
契约造成的理解负担。目标、项目、行动事项已经独立到 Umeda 工作管理，本轮不重设计、
不迁移，也不让白板持有第二份业务状态。

- 卡片承载内容，白板引用卡片并保留思考布局；同一卡片可以出现在多张白板。
- 摘要、研究、知识、反思和方法作为内容用途或模板，不要求逐级流转。
- AI 内容保留审核，但移动、连线、分组、引用和标签调整不触发审核。
- 用户只在不同设备间接续使用，不建设多人实时协作或 CRDT；继续保留既有离线队列、
  条件保存和可恢复冲突副本，防止未上传内容被静默覆盖。

参考：[基本元素](https://wiki.heptabase.com/fundamental-elements)、
[知识生命周期（2021 年愿景）](https://wiki.heptabase.com/the-knowledge-lifecycle)、
[设计路线说明（2023）](https://wiki.heptabase.com/the-roadmap)。引用设计原则不代表
已接入 Heptabase 服务、代码或私有格式。

## 源码中的实际边界

共享入口改为 `KnowledgeApp`：随手记、白板、卡片库、标签、待审核和原资料库工具。
旧工作台代码与旧文档均保留，不改写原文件。旧目标／项目／行动和 Dashboard 不投影为
知识卡片；其他可读资料（含无类型笔记）可以直接进入卡片库。

新增笔记使用 `cards/<独立 ID>.md`，YAML 只存最小身份、标题和必要来源；正文保持
Markdown。既有 PDF、EPUB、图片沿原文件与阅读器使用，不转成 Markdown 副本。
新摘录保存来源卡片引用、来源哈希、阅读位置、当时原文和批注；不是复制整个原资料。

白板使用 `whiteboards/<独立 ID>.md`，frontmatter 为 `type: whiteboard` 与标题，正文为
version 1 的 JSON 布局。每个摆放对象有独立 ID，记录卡片引用、位置、尺寸和折叠；文字、
分区与连线属于白板。字段不进入普通阅读界面。布局不塞进 frontmatter，避免超过原索引
属性预算。错误或未来版本拒绝覆盖，不重置空白板；保存沿原有 240 KiB 编辑大小边界。

这是一种沿用现有文件协议的开放布局格式，不是已完成“所有实体独立 SQLite 表”的重构。
SQLite 和内容文件依然由现有 LibraryService 宿主管理，页面只发命令，不直接操作宿主数据库。
没有新增远程协议、后台轮询、数据库 migration 或中转部署要求。

卡片引用优先使用显式 `card_id`，其次使用现有 `documentId`；缺身份的旧文件兼容路径引用
与移动别名。带身份的卡片缺失时不根据同路径猜测替代对象。移出白板只移除摆放与关联连线，
不删除原卡片；撤销／重做只作用于当前打开白板的布局编辑。

## 保存和审核

CardRepository 复用 LibraryModel 的 `saveText` / `readText`，卡片与布局进入同一宿主持久
队列和既有 Vault 同步。保存成功仅指本机接受，侧栏另显示待同步与同步状态。没有承诺备份、
生产部署或手机后台持续执行。新文档回执可能先于页面描述到达，读取初始版本失败时仅补一次
目录刷新，不为空白内容兜底。

识别 `generated_by` / `extracted_by` 的 ai、mixed，以及旧 `agent_claim` 来源。审核保存
Markdown 正文 SHA-256，正文变化后需要复核；改标签、改布局不改变审核。待审核页按主人
打开时读取 AI 正文，不调用模型，也不把整库送进 Agent。未标记来源的历史文件不猜测为 AI。

Desktop 的共同 `write_knowledge_document` 宿主入口已对新建 `cards/*.md` 和显式
`type: card` 文档补上 AI 来源，现有卡片 ID 由宿主保留。AI 不能用提交审核哈希的方式认可
自己的新正文；仅改标签时保留上一版人工审核。来源补写与正文在同一次条件替换中落盘，
不另建旁路账本。三个引擎复用同一入口；源哈希回执对应实际保存后的字节。

这不改写普通历史文档、系统文件、白板布局或纯文本格式；已损坏的历史属性保留供修复；Agent 提交的新卡片属性有误时拒绝写入，避免卡片身份与审核来源丢失。
原生 shell 直接写文件不经过这个入口，未标记来源时不能推断为 AI，因此不能宣称捕获了
所有写入。批量审核和退回 AI 修订的工作流尚未实现。
卡片正文编辑默认隐藏旧生命周期字段，高级原文编辑仍可修复属性。

## 第二个实现切片（0.5.0，2026-11-24）

- 白板卡片按进入可视范围加载笔记正文、图片和 PDF 页预览；PDF 可选择页码。沿用宿主
  附件缓存和大小限制，预览不复制原文件、不从远程 CDN 加载阅读器。EPUB 仍在原阅读器打开。
- 拖动分区时，拖动开始时完整包含在区域内的摆放对象随之移动；多选和嵌套分区不重复
  应用位移。它是空间分组，不引入必须维护的父子数据关系；删除分区保留卡片。
- 选中笔记／摘录，或包含它们的分区，可以请求 AI 总结、比较、找矛盾。先保存白板中的
  结果占位，再交给普通 Cindy 执行任务；结果卡同步后自动替换占位，保留来源引用。
  PDF／图片需先摘录为文本，不默认把原附件发给模型。正文超出普通消息预算时，提供
  明确的来源路径与版本哈希，要求执行任务读取完整原文，不把截断片段冒充全文。
- Desktop 使用公开的 `cindy.tasks.capabilities/create/send`，不自建 Agent、模型选择、
  执行权限或轮询。插件增加 `agent.tasks` 声明；实际安装／更新走宿主已有权限流程。
  不支持该公开能力的宿主明确提示。手机打开已有的新建执行任务页并填入草稿，由主人
  在普通入口选择执行设备和发送；桥回执的“草稿”不表示模型已执行。
- 每次提交使用固定请求标识；结果未到时可继续同一提交，不自动创建另一份执行任务。
  来源正文和白板不允许被该动作改写。执行状态、取消和模型报错仍由普通执行任务页承载。
- 人工认可正文时，将正文快照保存在 `90_系统/umeda/reviews/<引用哈希>-<正文哈希>.md`，
  卡片记录快照路径与正文哈希，沿原队列同步，不新增数据库 schema。AI 再改正文时保留
  上一版认可记录；默认阅读和白板预览继续展示已认可内容。主人可打开原文并排对照，
  接受 AI 修改或保留原版；不是逐行高亮 diff。首次生成无旧版时沿用简单认可入口。
  主人亲自编辑并保存正文即认可该版本，不再要求主人审核自己的修改。

## 验证与后续

- 定向 unit：真实 LibraryService / CloudVault 的离线重开、第二本机副本读取、跨白板引用、
  移动后身份、移出不删卡、正文审核、未来版本保留与 UI 桥回执时序；追加分区整体移动、
  认可快照／恢复、AI 输入来源版本和公开执行入口幂等提交。并入原测试文件（本机单文件
  约 2.5 秒）。Desktop Vault 测试追加宿主来源、稳定 ID、标签变更保留审核和新正文不能
  自审，约 1.4 秒。Mobile 桥测试验证草稿衔接和无效输入拒绝，约 2 秒。
- `scripts/whiteboard-smoke.mjs`：隔离 Electron 配置与合成云端，检查创建、编辑布局、重开、
  跨白板复用和反向位置、移出保留、双主题及窄屏截图，不接触个人资料。还检查实际拖动
  连线／分区、PDF 画布完成绘制、图片实际解码、摘录返回原文、顺序跨端布局刷新，以及
  合成 AI 结果落卡后的认可、修改对照、保留原版和接受新版。
- 共享包、Desktop 与 Mobile 类型检查通过，资料库原有阅读／离线端到端检查通过。
  通用 `ui:check` 的全页面构建以 `EPIPE` 中断，未计为通过；本包以独立白板和阅读器
  端到端检查及双主题截图验证，不把通用检查的未完成隐藏为成功。
- AI 端到端使用合成结果接真实资料保存链路，不调用真实模型。公开执行 API 已按当前
  仓库实现和测试核验；运行中客户端的版本／源码对应关系未确认，尚未安装升级插件，
  不宣称已验证真实模型运行或实际插件宿主的完整权限流程。Forge 已校验打包；本机
  示例端点产物只用于校验，正式使用前须以实际资料服务配置重新打包。
- 浏览器窄屏不等于 iPhone 实机；安装、iOS 原生桥／输入与触摸、网络切换仍需专项验收。
- 子白板和白板层级、块级引用、分享、导出完整布局与旧库迁移待实现。
  不因统一卡片而默认合并物理存储、复制原文件或直接删除旧对象。
